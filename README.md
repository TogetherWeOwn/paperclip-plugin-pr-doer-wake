# togetherweown.pr-doer-wake

Wakes the Paperclip card that owns an open, non-draft GitHub pull request, **at most once** per (PR, head SHA, state) (see "Delivery contract"):

| state | trigger |
|---|---|
| `review_findings` | `check_run` completed, name `Paperclip Review`, conclusion `failure` (complete assessment below `ratingThreshold`, `githubReviewConclusion` in `server/src/services/chat-github-review-policy.ts:229`). `action_required` (admission refusal, incomplete) never wakes. |
| `ci_red` | `check_run` completed with `failure`, `timed_out` or `startup_failure` on the PR's current head. `cancelled`, `stale`, `skipped` and `neutral` never wake. `requiredChecks` narrows to required names per repo. Commit `status` events are not consumed (see "Webhook events"). |
| `conflict` | `push` to a repo's default branch marks it; the 5-minute job reads open-PR mergeability (`sweepMaxPages` pages of 50 per repo per tick, default 4; a bigger repo resumes from the saved cursor next tick and logs a warning) and wakes owners of `CONFLICTING` PRs. Also `pull_request` `opened`, `reopened`, `synchronize`, `ready_for_review` and `edited` on an open non-draft PR, whatever the payload's `mergeable_state` (GitHub computes mergeability lazily, so these payloads usually say `unknown` with `mergeable: null` even for a conflicting PR): the PR is read from GitHub, `CONFLICTING` wakes, `UNKNOWN` is deferred (`error`) and read again by the job with backoff, anything else is skipped as `not_conflicting` without keeping a ledger row. This covers a conflict on a new PR or a new head after the last default-branch sweep finished. Each such delivery costs one GraphQL read unless its fingerprint is already settled; it resolves no secret beyond the cached ones (see "Webhook events"). |

Drafts, closed and merged PRs, superseded heads, fork PRs, outsider authors, stopped repos and cards whose ownership is ambiguous never wake. There is no merged wake: a merged PR has nothing left to fix (an old config listing `merged` in `wakeStates` is ignored).

PR state: before any wake, the plugin reads the PR from GitHub GraphQL (`githubTokenSecretRef`, required when enabled) and wakes only if it is open, non-draft, trusted and still on the signal's head; for `conflict`, still `CONFLICTING`; for `ci_red` and `review_findings`, the same read lists the latest check runs on the head commit (`checkSuites`, `checkRuns(filterBy: {checkType: LATEST})`, 100 per page; further pages of suites and of each suite's runs are read until `pageInfo.hasNextPage` is false, so no run is ever out of reach), and GitHub's newest run of a relevant check name in a check suite must be completed and red. A run supersedes only runs of the same name in its own suite: an independent suite (another GitHub App or workflow) exposing the same name, which passed later, never hides a genuine failure. Relevant: for `review_findings` the review check only; for `ci_red` every gating check (`requiredChecks`/`ignoreChecks`, never the review), because the state is per head. So if the delivered check recovered but another gating check is still red on the same head, the wake still happens with that check as the evidence, and no per-check evidence has to be kept in the ledger. A newer passing run, a re-run in progress, or the same run updated to passing (a re-scored Paperclip Review) with nothing else red ends the signal as `check_not_red`; the re-run's own completion delivery starts again. If GitHub does not list the delivered run yet, or still lists it as not completed (its view lags the webhook), the signal is deferred and read again. Webhook payloads never authorize a wake: they arrive late, out of order and with tied `updated_at` values, and converting to draft or closing does not change the head. A failed or rate-limited lookup fails closed (claimed as `error`, re-read later). A PR missing from a visible repository is closed: `NOT_FOUND` on `repository.pullRequest` ends the signal as `skipped_closed` and deletes a pending row after one read and one warning (`pr-doer-wake: GitHub says the pull request does not exist; treated as closed`). `NOT_FOUND` on `repository` is not: GitHub answers it the same for a private repo the token cannot see, so it is treated like a missing permission (see "GitHub token"): logged at level error, the signal kept as `error` and retried with backoff (hourly at most), and a repo's pending conflict sweep kept and read again each tick, as for any failed sweep read. To give up on a repo that was really deleted, list it in `stoppedRepos`. Any other GraphQL error stays transient.

Trust: a PR may name a card only if its head branch lives in the base repo (GraphQL `isCrossRepository: false`) and its author is `OWNER`, `MEMBER` or `COLLABORATOR`, or a login in `trustedAuthors` (bots report `NONE`; `[bot]` suffix and case are ignored).

## Webhook events

Subscribe the GitHub org webhook to exactly `pull_request`, `check_run` and `push` (content type `application/json`, secret = `webhookSecretRef`). Everything else is acknowledged without work, but still costs a stored row:

- Retention gap (host): `POST /api/plugins/:pluginId/webhooks/:endpointKey` inserts every delivery, headers and full payload, into `plugin_webhook_deliveries` before the worker sees it (`server/src/routes/plugins.ts` "Step 6"), and nothing in `server/src` prunes that table (only uninstall grace, PLUGIN_SPEC.md section 25). The plugin cannot filter before the insert, so the only lever here is the subscription list. Upstream note, not filed yet (search existing issues first per CONTRIBUTING.md): a retention window for `plugin_webhook_deliveries` (age or count per plugin), or an optional manifest-declared event allowlist the route checks before inserting.
- The route is public and also accepts the plugin key instead of the id (`resolvePlugin`, `routes/plugins.ts:377`), so anyone can POST to it. Deliveries are pre-filtered (`mayAct`), signatures must be well-formed `sha256=<64 hex>`, and verification uses a worker-memory copy of the webhook secret (`src/secrets.ts`: 10-minute TTL, keyed company + config path + secret id + version). One resolution per key runs at a time and concurrent deliveries await it (the SDK dispatches host requests concurrently). A value past its TTL still verifies (an HMAC match proves authenticity) and schedules one background re-resolution, which replaces it when the secret was rotated. The cache fails closed: a re-resolution that fails for any reason other than the host rate limit (secret deactivated, binding removed, secret deleted) evicts the value at once, and an expired value is never used more than 30 minutes after it was resolved, even while resolutions are rate-limited. Deactivating a leaked secret therefore stops it verifying within one TTL plus one delivery, without a config change or worker restart. Only a verification miss re-resolves on the request path, at most once per minute per company, so forged traffic cannot drain the host's 30-per-minute secret-resolution limit (`plugin-secrets-handler.ts:195`), which every secret of this plugin shares. The GitHub token shares the cache, with a negative cache: a failed resolution (binding removed, secret deactivated or deleted, host rate limit) is not retried for 1 minute, and after an HTTP 401 the token is not re-resolved for 5 minutes. Lookups meanwhile are transient and retried later, so an unbound or dead token costs at most one resolution per minute, however many signals arrive.

## Why a plugin

Paperclip has no path from a PR result to the doer's card: `chat-github-checks.ts:25` "This outbox never schedules an agent", the review publish (`chat-github-reviews.ts:1371`) logs `chat_github.published`, which `activity-log.ts:17-45` does not forward to plugins, and external objects (`github-external-object-provider.ts`) only track open/merged/closed and wake nobody. GitHub webhooks into `POST /api/plugins/:pluginId/webhooks/github` are the intended plugin ingress (PLUGIN_SPEC.md section 18).

## Guarantees

- Delivery contract: **at most once per (PR, head, state), not exactly once.** A double wake never happens; a missed wake is possible in one case (below), accepted, and counted. The host cannot support exactly once: `server/src/services/heartbeat/queue.ts` does not dedupe plugin `idempotencyKey`s (see "Phases"). Mechanics: an atomic `INSERT ... ON CONFLICT DO NOTHING` on `(company_id, fingerprint)` in the plugin's own namespace table `wake_ledger`, then, right before `requestWakeup`, a conditional wake mark (`UPDATE ... SET wake_attempted_at = <this attempt's value> WHERE wake_attempted_at IS NULL AND <claim fence>`) that only the attempt still holding the row can win. A wake that may have reached the host is never requested again.
- Claim fence: every write an attempt makes (phase marks, outcome, wake mark) carries `AND created_at = <its claim> AND attempts = <its claim>`. A new claim writes its own random-microsecond token as `created_at`; every re-claim bumps `attempts`. An attempt that stalled past the 10-minute stuck window (for example inside `createComment`) while the sweep took its row and decided it (say `ambiguous_card` after a second PR-link comment appeared), or deleted it and a newer signal claimed the fingerprint again, matches nothing when it resumes: it records nothing, never marks the wake and never overrides the newer decision (reported as a `duplicate`, `superseded by another attempt`). A signal folded into an attempt (below) changes neither column, so it never stops that attempt. No column was added.
- The accepted missed wake: if the worker dies after the wake mark commits and before `requestWakeup` returns, or the host's reply is lost or times out, the plugin cannot tell "accepted" from "never arrived". The row ends as `wake_unconfirmed` and that fingerprint may get zero wakes (a new head or state wakes normally). It is observable: the ledger outcome `wake_unconfirmed`, and one warning per case with the fixed message `pr-doer-wake: wake_unconfirmed (request sent, result unknown; not repeated)` in the host's `plugin_logs` (count them there; the plugin needs no `metrics.write` capability for this). The count is an upper bound on missed wakes: if `requestWakeup` succeeded but recording `woken` then failed, the wake mark stays, the row is never requested again and is later closed as `wake_unconfirmed` too (logged once as `pr-doer-wake: woken, but recording the outcome failed`); the same if `requestWakeup` hung past the 10-minute stuck window and the sweep closed the row first. Each row is logged as `wake_unconfirmed` at most once: only the attempt that holds the row's claim writes and logs it. Only `requestWakeup` itself is classified; nothing that fails after it returned can release the mark. Host refusals are not in the gap either: the host throws them before queueing anything (it writes only a skipped request), and they are recognised by their exact messages, never by keywords (the host answers every handler error as `-32603` with the bare message, so the code tells nothing). Final refusals end as `refused:<message>`, are not retried by the sweep, and release this attempt's wake mark (nothing was queued), so like a hold (see "Temporary skips") a later genuine signal on the same head and state resumes them: `Issue has no assigned agent to wake`, `Issue is not wakeable in status: <status>`, `Issue is blocked by unresolved blockers`, `Agent not found`, `Agent no longer exists`, `Agent is not invokable in its current state` (a paused, terminated or pending doer), `Agent is not invokable because its reporting chain is invalid`, and the budget reasons of `budgets.ts` (hard-stop reached or exceeded, unpriced usage, a paused company or project, a budget pause without a policy). The two that ask to wait while run accounting settles (`<Company|Agent|Project> cannot start work while completed runs await accounting.`, `New work must wait while a native run recovers its unfinished accounting.`) release this attempt's mark, so the sweep retries them with backoff. Any other message, however it reads, is `wake_unconfirmed`. Failures that prove the request never left are not in the gap: if the wake mark's own DB write fails (even with the commit landed and only the reply lost), the host answers `WORKER_UNAVAILABLE` with `Plugin is held for idle sleep` (answered before dispatch in `plugin-worker-manager.ts` `handleWorkerRequest`), or the SDK refuses before sending (`worker RPC host is not running`), this attempt's own mark is released and the wake is retried. The same `-32000` code with any other message (the SDK's `cleanup()` "Worker RPC host is shutting down", the host's `rejectAllPending` on a worker exit) answers a call that was already sent, so it is `wake_unconfirmed`, never retried.
- Temporary skips and holds never burn the fingerprint. A row exists only while a wake is pending, held or refused, or once one was decided (woken, unconfirmed, ambiguous, shadow). When a retry finds the PR draft, untrusted, closed, re-pushed, no longer conflicting, its checks not red (yet), or the repo stopped, the never-woken row is deleted (`DELETE ... WHERE wake_attempted_at IS NULL AND updated_at = <this attempt's claim token>`), and the webhook path never writes one for a skip. A later genuine signal on the same head and state (a flaky check re-run that fails again, a PR marked ready) can therefore still wake. A hold on the card (`held_status:<status>`, `held_blockers`, a host `refused:<message>`) never requested a wake (or the host refused it before queueing anything), so its row stays resumable: the sweep does not poll it, but the next genuine signal for that fingerprint (a new failing run, a redelivery, the conflict sweep after a default-branch push) resumes it, re-reads GitHub and the card, and wakes once the blocker cleared or the card is active again. `ambiguous_card` and `shadow` stay settled (fail closed).
- A signal is never acknowledged as settled while an attempt that may still delete the row is in flight. A signal for a fingerprint whose row is `claimed` or `retrying` with no wake requested (for example a second gating check failing while a retry reads GitHub) is folded into that attempt: it stores the newest signal and moves `updated_at` by one microsecond, which voids the attempt's claim token (each retry writes its own random-microsecond token as `updated_at` when it takes the row). If that attempt then wakes, the folded signal is covered by the same (PR, head, state) wake; if its GitHub read finds nothing red, its conditional delete matches nothing because the read may predate the folded signal, so the row stays `error` and the sweep re-reads GitHub. A signal that loses the row to another attempt between its pre-check and its own claim looks at the row again (up to four rounds; past that it is logged as `the ledger row kept changing` and reported as `error`). No column was added: `updated_at` is the row version.
- Retries: rows at `error` (GitHub or the secret unavailable, a step failed before the wake) and `no_card` (no owning card yet, or the owner's assignee is missing or excluded) are retried with an exponential backoff of 2, 4, 8, 16, 32, then every 60 minutes, with no attempt cap; rows stuck at `claimed` or `retrying` after 10 minutes (the worker stopped mid-attempt). A pending row ends only when a retry decides it: woken, held, or deleted because GitHub says the PR no longer qualifies (closed, merged, re-pushed, draft, check green). So a GitHub, token or secret outage of any length never loses a signal that the webhook already acknowledged; it costs at most one GitHub read per pending row per hour, and the secret cache's negative caching keeps an unbound or deleted secret at one resolution per minute. A repo's pending conflict sweep (one per repo) is likewise kept until one full read of its open PRs succeeds with no `UNKNOWN` mergeability; failed or `UNKNOWN` ticks keep it, whatever their number. An authenticated redelivery, or another failing check on the same head and state, resumes an `error`, `no_card`, held or refused row at once instead of waiting for its backoff; a row in flight takes the signal over (see above); a row whose wake was attempted or decided stays a duplicate and costs no GitHub lookup. Every retry first takes its row with a conditional `UPDATE ... WHERE outcome = <selected> AND updated_at = <selected>` and proceeds only on `rowCount = 1`, and only one sweep runs per worker at a time (the host releases its job overlap guard on its 5-minute timeout without cancelling the worker call, so a slow sweep could otherwise meet the next tick). Before every retry it re-applies the current `stoppedRepos`/`wakeStates`, re-reads the PR from GitHub and re-resolves the owning card (see "Card resolution"). Pending conflict sweeps for a repo stopped after the push are dropped without reading GitHub.
- Retention: 30 days after a row was settled or held (`woken`, `wake_unconfirmed`, `ambiguous_card`, `shadow`; and `refused`, `held_status`, `held_blockers`, which only a later genuine signal resumes, with its own payload) it keeps only its dedupe key and outcome (`signal` is emptied); rows are never deleted, so a still-open PR on the same head in the same state never wakes twice however late the next signal comes. A tombstone is a few hundred bytes. A pending row (`claimed`, `retrying`, `error`, `no_card`, an earlier build's `stale:<reason>`) is never compacted, however old (for example of a company disabled for a month), so it still wakes once it can. A pending row an earlier build did compact is resumed by the next genuine signal, which brings its own payload.
- Phases: `comment_posted_at` and `wake_attempted_at` (migration 002) record what an attempt already did. A retry posts the evidence comment only if neither the phase nor an identical comment on the card exists. Once `wake_attempted_at` is set and no success reply was recorded, the row ends as `wake_unconfirmed` (see "Delivery contract"). The host can accept a plugin wake as a new run, coalesce it into a running one or persist it as a deferred request with no run (`server/src/services/heartbeat/queue.ts` ~3733-3740 and ~4110-4118), it does not dedupe plugin `idempotencyKey`s (only `execution-reconciliation:` keys), and plugins cannot read `agent_wakeup_requests`, so no plugin-side check can prove a lost request was not accepted. Upstream exit (not filed yet; search first per CONTRIBUTING.md): have `requestWakeup` dedupe on a plugin `idempotencyKey` and return the existing receipt, which would let a retry safely repeat the call.
- Holds: cards in `backlog`/`done`/`cancelled`, with an unresolved `blockedBy`, or (with `skipBlockedStatus`) in `blocked` get no comment and no wake; the next genuine signal resumes the row (see "Temporary skips"). Every attempt, retries included, re-reads the card and treats it as `no_card` if its current assignee is missing or in `excludeAgentIds`. `ctx.issues.requestWakeup` re-checks assignee, terminal status, blockers, budgets and the agent's state on the host (`server/src/services/plugin-host-services.ts:2354-2374`, `heartbeat/queue.ts` `enqueueWakeup`); its refusals are classified as above.
- The evidence comment is plugin-authored; plugin comments never wake anyone (SDK `createComment` doc). The wake is `requestWakeup` with reason `github_pr_<state>`.
- `shadow: true` (the default) records `shadow:<card>` in the ledger and wakes nobody.

## Card resolution (interim)

Core reads: `issues` and `issue_comments` only (card resolution, evidence-comment check). Plugins cannot read `issue_work_products` (not in `PLUGIN_DATABASE_CORE_READ_TABLES`, `packages/shared/src/constants.ts:1442`). Until upstream adds it, both of these are looked up, whatever the card's status or current assignee:
1. the card named by the head branch (`TOG-123-slug`), and
2. every card on which an agent posted the exact PR URL in a comment (the doer's PR-link comment; up to two are read). Only an actual `https://github.com/<org>/<repo>/pull/<n>` link counts (case-insensitive): it must start at the beginning of a line or after a character that cannot sit inside a URL (whitespace, `(`, `[`, `<`, `*` and the like), and end at a non-digit. Another host (`https://notgithub.com/...`), a GitHub URL embedded in another URL (`https://evil.io/?u=https://github.com/...`), a scheme-less `github.com/...` and `/pull/<n>3` never count. Both SQL predicates enforce it (`ILIKE '%https://github.com/<org>/<repo>/pull/<n>%'` and a `~*` regex with both boundaries, `src/sql.ts` `prUrlPatterns`). Comments by `excludeAgentIds` (the Reviewer), by people and by plugins, and `chat_channel` cards, never count. The card's current assignee plays no part, so handing the owner to the Reviewer cannot promote another card.

Ownership is decided first and eligibility only afterwards. The owner is the single card both paths together name. Two or more distinct candidates (the branch and a comment disagree, or PR-link comments sit on two cards, whichever came first) hold the wake as `ambiguous_card`: no comment, no wake, not retried; fail closed, never another card. A retry re-resolves the owner as well: if the evidence no longer names exactly the card an earlier attempt chose (and may have commented on), it is held as `ambiguous_card` instead of waking or retargeting. Otherwise an ineligible owner holds the wake on itself (`held_status:done`, resumed by the next genuine signal, or `no_card` with the owner recorded while it is assigned to an excluded agent or nobody, retried with backoff so it wakes once the doer has it back) instead of passing it to another card. None found is `no_card` (retried as above). Cost of failing closed: a PR whose link was also posted on a second card by a non-excluded agent (a parent or summary card) never wakes from this plugin.

Measured against `issue_work_products` on 341 live PRs (2026-10-27, with the earlier first-mention rule): 302/326 linked PRs resolve to the same card, 17 resolve to none, 8 to another card. The `ambiguous_card` hold now covers every wrong-card case where two candidates exist; a single candidate that is the wrong card is not detectable without `issue_work_products`.

## Config (per company)

`enabled`, `shadow`, `githubOrg`, `webhookSecretRef`, `githubTokenSecretRef` (both required when enabled), `excludeAgentIds`, `requiredChecks`, `ignoreChecks`, `stoppedRepos`, `wakeStates`, `skipBlockedStatus`, `postEvidenceComment`, `branchIdentifierPattern`, `trustedAuthors`, `sweepMaxPages`. See `src/manifest.ts`.

Secret fields carry `format: "secret-ref"` (PLUGIN_SPEC.md section 19.8), so the settings form shows a secret picker and the host binds the secret to the plugin. The picker stores `{ type: "secret_ref", secretId, version? }`, so the schema type stays `object`: with `type: "string"`, as the bundled sandbox providers use for their environment config (converted by `environment-config.ts` first), the host's Ajv check in `plugin-config-validator.ts` refuses that object with "must be string" (`tests/sql.test.ts` runs a verbatim copy of it).

### GitHub token

The token reads, per signal, the PR (`state`, `isDraft`, `isCrossRepository`, author, head, `mergeable`) and the check runs on its head commit, and for the conflict sweep the open PRs of a repo. It needs read access to pull requests and check runs in every repo of `githubOrg`:

- a classic personal access token: no scope for public repos, `repo` for private ones (classic tokens cannot be narrowed to read-only), or
- a token with repository permissions Pull requests: read and Checks: read (Metadata: read is implied). Commit statuses are not read.

Fine-grained personal access tokens cannot be granted Checks (GitHub offers that permission to GitHub Apps only), so check reads come back as `FORBIDDEN` "Resource not accessible by personal access token". A GitHub App installation token would work, but it expires after an hour, so it cannot sit in a static secret. A missing permission, or a repository the token cannot see (GitHub answers `NOT_FOUND` on `repository` for a private repo outside the token's reach, the same as for a deleted one), is reported as a config error: `pr-doer-wake: GitHub token cannot see the repository or lacks a permission (config error); the signal is kept and retried` at level error, with the repo and the GraphQL paths and error types that were refused. The signal is kept as `error` and retried with backoff (hourly at most, no cap), so it wakes once the token is fixed.

## Upgrading from 0.1.1

Set `githubTokenSecretRef` before upgrading: an enabled company without it fails config validation and is ignored. Check that the token can read check runs (see "GitHub token"). The `pr` plugin-state entries 0.1.1 wrote (the webhook PR index) are no longer read and are inert. The stored secret bindings keep their shape; only the schema gained `format: "secret-ref"`. Ledger rows that earlier builds closed as `stale:<reason>` (never woken) are resumed by the next genuine signal for their fingerprint; this build no longer writes them.
