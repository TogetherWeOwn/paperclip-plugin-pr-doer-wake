# togetherweown.pr-doer-wake

Wakes the Paperclip card that owns an open, non-draft GitHub pull request, once per (PR, head SHA, state):

| state | trigger |
|---|---|
| `review_findings` | `check_run` completed, name `Paperclip Review`, conclusion `failure` (complete assessment below `ratingThreshold`, `githubReviewConclusion` in `server/src/services/chat-github-review-policy.ts:229`). `action_required` (admission refusal, incomplete) never wakes. |
| `ci_red` | `check_run` completed with `failure`, `timed_out` or `startup_failure` on the PR's current head. `cancelled`, `stale`, `skipped` and `neutral` never wake. `requiredChecks` narrows to required names per repo. Commit `status` events are not consumed (see "Webhook events"). |
| `conflict` | `push` to a repo's default branch marks it; the 5-minute job reads open-PR mergeability (`sweepMaxPages` pages of 50 per repo per tick, default 4; a bigger repo resumes from the saved cursor next tick and logs a warning) and wakes owners of `CONFLICTING` PRs. Also `pull_request` payloads that already say `mergeable_state: dirty`, if GitHub still reports `CONFLICTING`. |

Drafts, closed and merged PRs, superseded heads, fork PRs and outsider authors never wake. There is no merged wake: a merged PR has nothing left to fix (an old config listing `merged` in `wakeStates` is ignored).

PR state: before any wake, the plugin reads the PR from GitHub GraphQL (`githubTokenSecretRef`, required when enabled) and wakes only if it is open, non-draft, trusted and still on the signal's head; for `conflict`, still `CONFLICTING`; for `ci_red` and `review_findings`, the same read lists the check's current runs on the head commit (`checkSuites`/`checkRuns` filtered by the check name, `checkType: LATEST`) and the newest one must be completed and still red. A newer passing run, a re-run in progress, or the same run updated to passing (a re-scored Paperclip Review) ends the signal as `check_not_red`, so a late failure delivery from an older run, or a retry after CI recovered without a new commit, never wakes. If GitHub does not list the delivered run yet (its view lags the webhook), the signal is deferred and read again by the sweep. Webhook payloads never authorize a wake: they arrive late, out of order and with tied `updated_at` values, and converting to draft or closing does not change the head. A failed or rate-limited lookup fails closed (claimed as `error`, re-read by the sweep). A redelivered red check that is already in the ledger costs no lookup.

Trust: a PR may name a card only if its head branch lives in the base repo (GraphQL `isCrossRepository: false`) and its author is `OWNER`, `MEMBER` or `COLLABORATOR`, or a login in `trustedAuthors` (bots report `NONE`; `[bot]` suffix and case are ignored).

## Webhook events

Subscribe the GitHub org webhook to exactly `pull_request`, `check_run` and `push` (content type `application/json`, secret = `webhookSecretRef`). Everything else is acknowledged without work, but still costs a stored row:

- Retention gap (host): `POST /api/plugins/:pluginId/webhooks/:endpointKey` inserts every delivery, headers and full payload, into `plugin_webhook_deliveries` before the worker sees it (`server/src/routes/plugins.ts` "Step 6"), and nothing in `server/src` prunes that table (only uninstall grace, PLUGIN_SPEC.md section 25). The plugin cannot filter before the insert, so the only lever here is the subscription list. Upstream note, not filed yet (search existing issues first per CONTRIBUTING.md): a retention window for `plugin_webhook_deliveries` (age or count per plugin), or an optional manifest-declared event allowlist the route checks before inserting.
- The route is public and also accepts the plugin key instead of the id (`resolvePlugin`, `routes/plugins.ts:377`), so anyone can POST to it. Deliveries are pre-filtered (`mayAct`), signatures must be well-formed `sha256=<64 hex>`, and verification uses a worker-memory copy of the webhook secret (`src/secrets.ts`: 10-minute TTL, keyed company + config path + secret id + version). One resolution per key runs at a time and concurrent deliveries await it (the SDK dispatches host requests concurrently). A value past its TTL still verifies (an HMAC match proves authenticity) and schedules one background re-resolution, which replaces it when the secret was rotated. The cache fails closed: a re-resolution that fails for any reason other than the host rate limit (secret deactivated, binding removed, secret deleted) evicts the value at once, and an expired value is never used more than 30 minutes after it was resolved, even while resolutions are rate-limited. Deactivating a leaked secret therefore stops it verifying within one TTL plus one delivery, without a config change or worker restart. Only a verification miss re-resolves on the request path, at most once per minute per company, so forged traffic cannot drain the host's 30-per-minute secret-resolution limit (`plugin-secrets-handler.ts:195`), which every secret of this plugin shares. The GitHub token shares the cache; after an HTTP 401 it is not re-resolved for 5 minutes (lookups meanwhile are transient and retried by the sweep), so a dead token cannot spend the webhook secret's budget.

## Why a plugin

Paperclip has no path from a PR result to the doer's card: `chat-github-checks.ts:25` "This outbox never schedules an agent", the review publish (`chat-github-reviews.ts:1371`) logs `chat_github.published`, which `activity-log.ts:17-45` does not forward to plugins, and external objects (`github-external-object-provider.ts`) only track open/merged/closed and wake nobody. GitHub webhooks into `POST /api/plugins/:pluginId/webhooks/github` are the intended plugin ingress (PLUGIN_SPEC.md section 18).

## Guarantees

- Delivery contract: **at most once, not exactly once.** Atomic `INSERT ... ON CONFLICT DO NOTHING` on `(company_id, fingerprint)` in the plugin's own namespace table `wake_ledger`, and a wake that may have reached the host is never requested again. The residual gap: if the worker dies after the wake mark commits and before `requestWakeup` returns, or the host's reply is lost or times out, the plugin cannot tell "accepted" from "never arrived", so the row ends as `wake_unconfirmed` (warning in the log) and that fingerprint may get zero wakes. Closing that gap needs the upstream receipt below; until then this weaker contract has to be accepted explicitly before deployment. Failures that prove the request never left are not in the gap: if the wake mark's own DB write fails (even with the commit landed and only the reply lost) or the host answers `WORKER_UNAVAILABLE` (idle hold, answered before dispatch in `plugin-worker-manager.ts` `handleWorkerRequest`), the mark is released and the sweep retries.
- Retries: the sweep finishes rows at `error` (after 2 minutes), rows stuck at `claimed` or `retrying` (after 10 minutes, the worker stopped mid-attempt) and rows at `no_card` (after 5, 10, 15, 20 minutes: the doer's PR-link comment often lands after a fast check), up to 4 retries per row. Each retry first takes its row with a conditional `UPDATE ... WHERE outcome = <selected> AND updated_at = <selected>` and proceeds only on `rowCount = 1`, and only one sweep runs per worker at a time (the host releases its job overlap guard on its 5-minute timeout without cancelling the worker call, so a slow sweep could otherwise meet the next tick). Before every retry it re-applies the current `stoppedRepos`/`wakeStates` and re-reads the PR from GitHub: stopped repos, draft, closed, merged, re-pushed, untrusted or recovered PRs end as `stale:<reason>` and are never woken. A PR lookup that fails transiently (GitHub 5xx, secret rate limit, rejected token) is claimed as `error` and re-read by the sweep instead of dropped. Pending conflict sweeps for a repo stopped after the push are dropped without reading GitHub.
- Retention: after 30 days a ledger row keeps only its dedupe key and outcome (`signal` is emptied); rows are never deleted, so a still-open PR on the same head in the same state never wakes twice however late the next signal comes. A tombstone is a few hundred bytes.
- Phases: `comment_posted_at` and `wake_attempted_at` (migration 002) record what an attempt already did. A retry posts the evidence comment only if neither the phase nor an identical comment on the card exists. Once `wake_attempted_at` is set and no success reply was recorded, the row ends as `wake_unconfirmed` (see "Delivery contract"). The host can accept a plugin wake as a new run, coalesce it into a running one or persist it as a deferred request with no run (`server/src/services/heartbeat/queue.ts` ~3733-3740 and ~4110-4118), it does not dedupe plugin `idempotencyKey`s (only `execution-reconciliation:` keys), and plugins cannot read `agent_wakeup_requests`, so no plugin-side check can prove a lost request was not accepted. Upstream exit (not filed yet; search first per CONTRIBUTING.md): have `requestWakeup` dedupe on a plugin `idempotencyKey` and return the existing receipt, which would let a retry safely repeat the call.
- Holds: cards in `backlog`/`done`/`cancelled`, with an unresolved `blockedBy`, or (with `skipBlockedStatus`) in `blocked` get no comment and no wake. Every attempt, retries included, re-reads the card and treats it as `no_card` if its current assignee is missing or in `excludeAgentIds`. `ctx.issues.requestWakeup` re-checks assignee, terminal status, blockers and budget hard-stops on the host (`server/src/services/plugin-host-services.ts:2354-2372`).
- The evidence comment is plugin-authored; plugin comments never wake anyone (SDK `createComment` doc). The wake is `requestWakeup` with reason `github_pr_<state>`.
- `shadow: true` (the default) records `shadow:<card>` in the ledger and wakes nobody.

## Card resolution (interim)

Core reads: `issues` and `issue_comments` only (card resolution, evidence-comment check). Plugins cannot read `issue_work_products` (not in `PLUGIN_DATABASE_CORE_READ_TABLES`, `packages/shared/src/constants.ts:1442`). Until upstream adds it, both of these are looked up, whatever the card's status or current assignee:
1. the card named by the head branch (`TOG-123-slug`), and
2. the card whose own assignee first posted the exact PR URL in a comment (Reviewer and `chat_channel` cards excluded).

Ownership is decided first and eligibility only afterwards: if both find a card and they differ, the wake is held as `ambiguous_card` (no comment, no wake). Otherwise the card either path found is the owner, and an ineligible owner holds the wake on itself (`held_status:done`, or `no_card` while it is assigned to an excluded agent) instead of passing it to another card that merely mentioned the PR. None found is `no_card` (retried as above).

Measured against `issue_work_products` on 341 live PRs (2026-10-27): 302/326 linked PRs resolve to the same card, 17 resolve to none, 8 to another card. The `ambiguous_card` hold covers the wrong-card cases where both paths disagree; a single path that picks the wrong card is not detectable without `issue_work_products`.

## Config (per company)

`enabled`, `shadow`, `githubOrg`, `webhookSecretRef`, `githubTokenSecretRef` (both required when enabled), `excludeAgentIds`, `requiredChecks`, `ignoreChecks`, `stoppedRepos`, `wakeStates`, `skipBlockedStatus`, `postEvidenceComment`, `branchIdentifierPattern`, `trustedAuthors`, `sweepMaxPages`. See `src/manifest.ts`.

## Upgrading from 0.1.1

Set `githubTokenSecretRef` before upgrading: an enabled company without it fails config validation and is ignored. The `pr` plugin-state entries 0.1.1 wrote (the webhook PR index) are no longer read and are inert.
