# Threat model: CI registration and opt-in PR custody

Status: implementation review required; this is not Security acceptance. Maintainer role: plugin toolsmith. API targets: stock plugin SDK 2026.1023.0 and GitHub REST 2022-11-28.

## Assets and credential ceiling

Assets are the GitHub bearer credential OR App RSA private key and short-lived installation tokens, optional webhook HMAC secret, exact card-to-head registration, host wake budget, and the non-secret wait/audit ledger. The configured credential/private key may be broader than the plugin's repo allowlist; that residual ceiling must be recorded by the Operator and independently dispositioned by Security. App mode exchanges an existing approved key for repository/permission-narrowed tokens; it does not create/rotate an App key, modify installations or authorize additional grants. No billable infrastructure is created, and no builds execute in the credential-bearing worker.

The following table describes the unchanged **CI registration path**, not the custody or gates additions below.

| Credential can potentially do | CI path exposes | Explicitly forbidden on CI path |
| --- | --- | --- |
| Read resources within its GitHub grant | Fixed-origin GET of PR, base rules/classic required status checks, commit checks/suites/statuses, exactly associated Actions workflow attempts/jobs for allowlisted registered heads | Arbitrary URLs, headers, paths, search, repository enumeration, writes, merges, workflow mutation/dispatch/rerun, arbitrary token minting |
| App key can request tokens up to its installation grant | Fixed-origin POST to the configured installation; exactly one allowlisted repository, pull_requests/checks/statuses/actions/administration/metadata read on every mint; strict returned scope/expiry validation | Scope omission, all-repo fallback, bearer/anonymous fallback, agent-supplied App identity, installation/grant changes |
| Authenticate one webhook origin | Compare SHA-256 raw-body HMAC and trigger the same bounded recheck | Payload-directed issue selection or direct wakes |
| Paperclip SDK capabilities | Checkout-owner assertion, exact card/workspace reads, plugin state, job, one wake API | Issue create/update/comments, SQL/core tables, shell, secret output |

## Principals and boundaries

Tool run context (company/project/agent/run) is host-supplied, never an argument. `issueId` is an untrusted selector until `assertCheckoutOwner` succeeds. The card company/project and execution workspace repository/branch must match the current PR head. The assertion and binding are rechecked after GitHub responds. The runtime does not infer the owner from a `work/<uuid>` prefix, PR body, issue description, comment, author name or provider error.

The registration binds company, issue, project, workspace, branch, repo, PR number, SHA and registering run to a plugin-derived wait ID. Checkout can legitimately end before CI completes: scheduled rechecks revalidate card/workspace/configuration and let `requestWakeup` apply current assignee, blocker, terminal and budget constraints. The plugin never changes task status, assignment, monitor or review policy.

GitHub and Paperclip are separate systems. Revalidate current PR head/base and card/workspace before the wake. They cannot be atomically locked together; a change immediately after the final read remains a race. Branch/repository mutations retire or refuse the wait. Deleted fork repositories and missing bindings fail closed.

## Confused deputy and injection

The agent may supply a foreign issue, copied SHA, fork PR, spoofed branch, case tricks, encoded separators, oversized numbers, unknown keys or hostile natural-language content. Execution-time closed-schema parsing, checkout assertion, fixed GitHub origin, allowlist and authoritative workspace/PR reads constrain these. The runtime accepts no credential, secretRef, approval boolean, endpoint or caller identity in tool arguments.

PR/API content is data, not instructions. Only projected identifiers, statuses, check names, timestamps and app IDs affect readiness. App-bound checks cannot be satisfied by legacy commit statuses or an unrelated app of the same name. Unknown/partial shapes, denied pages, pagination limits and unknown conclusions stay pending. A required check failing does not wake while another required check remains pending. An active associated suite needs positive Actions attempt/job evidence before terminal required checks can ignore optional work. Discovery is constrained by exact repo/head/suite; complete attempt-job pages bind exact check-run references, names and conclusions, followed by suite/workflow rereads. Response-provided references are validated, never fetched. Missing/contradictory evidence and newer partial attempts defer, as do legacy statuses while observed suites run. This is not a transaction or an enumeration of uncreated rerun targets; universal required-only latency is not promised. Every extra GET uses the unchanged request/page/byte/cache/time budgets and operation-local credential. Actual existing Actions-read authority remains pre-installation evidence; denial is not permission to widen a credential.

## Secrets and transport

Resolve configured references only after tool authorization and before the authorized read/exchange. Bearer and App modes are mutually exclusive; incomplete/ambiguous/unknown config fails closed. App mode signs a five-minute RS256 JWT with 60s clock skew, validates 2048–8192-bit RSA, and validates exact returned repository and all six fixed read permissions including explicit metadata. The installation response is never ETag-cached. Only tokens are reused in private fields for a bounded 180s poll cycle, renewing inside the 60s expiry margin; keys and JWTs are not retained as fields. All entrypoints use this path. Errors are fixed code strings, not upstream/host exceptions or bodies. GitHub client rejects direct and JSON-escaped current-credential reflection anywhere in a response. Recognizable GitHub token/JWT/private-key-shaped fields from earlier cycles are removed before data or ETag bodies are retained; strict projections still refuse a removed identifier/status/check field, but unused PR/CI prose does not block readiness. ETag/Link credential shapes and unexpected exchange fields remain refusals, without retaining old secrets. Arbitrary unrecognized historical bearer strings cannot be identified by shape; this is defense in depth, not proof an upstream cannot disclose unknown secrets. Check labels reject control characters and are bounded before the wake reason. Tests use synthetic canaries only.

The cycle lifetime is **not** an upstream token TTL: GitHub tokens may remain valid for one hour, and are not explicitly revoked here. Ambiguous mint responses, process crashes and late host completion can leave valid orphan tokens until expiry. JS garbage collection is not secure erasure. Expiry, denied scope or revoked tokens never trigger broader fallback. Installation backoff spans companies, repositories and key-reference changes, independently of company-isolated ETag response caches. Both modes keep live throttles across response-cache eviction; a bounded full throttle table refuses new identities rather than dropping active backoff. This remains process-local state, not cross-worker coordination or restart persistence. Exchange requests consume existing global tick/client/time budgets. Invalidation is rechecked after secret resolution and before exchange, so a late secret RPC cannot initiate new credential creation after a client timeout. Private-key compromise still permits minting outside these requested scopes: token narrowing does not narrow key authority. The selected stock-compatible source route directly resolves the approved key at call time. A scoped-token broker could isolate that key from this worker, but requires a supported invocation contract and proved authorization, isolation, availability and endpoint coverage; no internal endpoint or assumed broker grant is introduced here. Security must explicitly disposition direct broad-key custody, the actual App grant ceiling and token cleanup residuals before install.

Use `ctx.http.fetch` on `https://api.github.com` only. Do not follow Link URLs; build page numbers locally. Client requests `redirect: error` and rejects a returned redirect/changed URL. **Stock-host limitation:** the pinned SDK serializes only selected RequestInit fields; enforcement of redirect refusal and network abort at the actual host must be verified before installation. The target host is reported to buffer up to **200 MiB** and provide **no request cancellation**. A response-size check in the worker (16 KiB for exchange, bounded reads otherwise) does not prevent that host allocation; acceptance deadlines bound only worker waiting. Independent Security must disposition the exact artifact/host/config risk before install, not infer acceptance from tests. Process separation is not an OS sandbox and does not constrain a compromised plugin with the broad credential in memory.

Some pinned SDK response wrappers construct a body-bearing Response for 304, which can throw. Conditional-read compatibility must use a real successful unconditional re-read within the same budget, never interpret an exception as cached success. Record target-host behavior in acceptance evidence.

## Replay, concurrency and state integrity

One host-managed worker serializes registration, job and webhook work. Same-run registration retries are stable; joining runs are recorded as bounded aliases. New-run rearming after a settled wait is explicit. This does not claim that the plugin can distinguish a mistaken new registration from an intentional manual rerun.

Before the wake API call, persist a `waking` intent and stable `(repo, headSha, waitId)` idempotency key. A lost reply or restart during the intent becomes `unconfirmed`, not an automatic retry. Host `queued: false` may retry on later polls because it confirms no wake queued. State/audit failure before an effect stops it; failure after a potentially delivered effect preserves the conservative intent/unconfirmed state. Retain the card backstop to cover this at-most-once-versus-delivery tradeoff.

**No cross-worker CAS is provided by stock plugin state.** Run one installed worker/ledger, not overlapping independent installations. A process-local lock is not evidence of distributed fencing. Security must accept or reject this deployment envelope explicitly.

Webhook verification uses timingSafeEqual, raw bytes, SHA-256 only, delivery UUID replay entries for 24 hours, repository/organization allowlists, 20-second head debounce and six hints/minute. Admission before the worker queue is limited to two outstanding hints and six candidate bodies/minute, before any ledger/configuration RPC. Six secret verifications/minute independently limit consumption of the host secret-resolution quota. Malformed/oversized payloads are rejected. Payloads without an existing exact-head registration create no wait. Dropped hints never bypass readiness; the independent four-minute poll catches them.

## Caps, expiry and audit

Immutable code limits bound open/retained waits, run aliases, audit ring, delivery replay records, cached HTTP responses, pages, bytes, tick duration, requests and wake attempts. Active waits expire after seven days without extension on retry. Independent scheduled compaction retires expiry and prunes 30-day tombstones and 24-hour delivery entries. TTL pertains only to plugin records; resource provisioning, spend reservations, delegated credentials and cloud teardown are not applicable because all provider operations on this path are reads.

The ledger records safe tool intent/outcome/refusal entries with server time and host run/company IDs. Wake intents/outcomes and webhook hints are also recorded. Audit writes precede new effects; arbitrary arguments, secrets, raw bodies, HTTP errors and headers are never audit fields. Older routine poll intents are evicted before wake/refusal evidence, while the newest call's intent is always persisted before credential access. Non-routine events can still exhaust the 1,000-entry cap; this is a bounded operational ring, not a tamper-evident compliance archive. Operator export/retention and host native immutable tool-event coverage remain installation evidence, not claims proved by unit tests.

## Residual risks and installation hold

- Compromised worker/host or an excessively broad upstream credential exceeds the narrow tool boundary. Use minimal grants and revoke bindings on compromise.
- Host may store unauthenticated webhook headers/raw bodies **before** plugin verification, without a plugin-controlled retention policy. Phase two stays off until the owner accepts ingress/storage and supplies the secret/webhook.
- A denied or unavailable rules/protection API cannot produce completion evidence. Repair access; never waive a check or substitute model judgment.
- Finite caps or the ambiguous-reply policy can miss a timely wake. Backstop monitors and `unconfirmed` audit review remain required operational controls; there is no canary trial or twenty-head acceptance gate.
- Governance of `ctx.tools.register`, redirect/timeout handling, native host idempotency and safe secret trace behavior must be verified on the exact installation. This repository alone does not prove them.

## Per-job addition: pr-custody

This scheduled operation is separately disabled and dry-run by default. It registers no new agent tool and cannot create CI waits. Its host/company/org/recipient/secret configuration is trusted Operator input, never PR text or model arguments. Same GitHub credential trust boundary, expanded **read** surface; native card/document writes are new and require renewed explicit Security acceptance before install.

| Credential/host ceiling | Custody exposes | Forbidden |
| --- | --- | --- |
| GitHub read grant | Fixed-origin GET organization repos, repo open/closed pulls, exact PR, PR issue comments; POST `/graphql` with generated PR commit/review/head-suite query and validated variables. Exactly one credential mode: bearer ref **or** the dedicated read-only App (`githubAppId`/`githubInstallationId`/`githubAppPrivateKeySecretRef`). App mode mints without a repository selection and refuses any mint whose returned permissions are not all `read` within the fixed six-permission ceiling, or whose listed repositories leave the configured org. | Arbitrary URL/query/header/provider method, search inventory, writes, webhook/settings changes, workflow dispatch/rerun, close/reopen/merge |
| Core-read tables | Company-scoped keyset SELECTs of issues, comments and document metadata, SDK document body reads, project/repo membership | Core SQL writes, undeclared document/work-product table joins, private runtime APIs, shell or credential discovery |
| Native issues/documents | One disposition document on an eligible source, or exact-origin `todo` child plus explicit native wake; one daily summary | Source assignment/status/review-policy changes, comments, inferred primary owner, automatic PR verdict or reopening a superseded proposal |

Assets additionally include company task/document content, ownership classifications, closure coverage, native agent execution budget and durable trigger receipts. Task content is consumed only by fixed URL/directive parsers. Nothing in it may change org/company, credential, request destination, caps or permitted operations. Output documents contain projected PR/head/trigger evidence, not raw task/API bodies. The generated origin/doc namespace is excluded from future evidence to prevent feedback loops. Human comments can record a disposition but do not establish URL ownership; all unrelated plugin/routine origins and terminal states remain eligible ownership candidates. Zero/multiple candidates are summary-only, not guessed assignments. Text/branch mapping is weaker evidence than explicit registration and is not transferred into the CI authorization path.

Cross-tenant checks occur in every SQL query, returned row/document identity and project-workspace binding. The configured company must agree between instance and company-effective configuration. Before effects, reread configuration, PR state/head and current source assignment/status and blockers; native host wake permissions remain authoritative. These are bounded reads, not a cross-system transaction: ownership/text/PR changes immediately after observation remain a residual race. Core SELECT privacy filtering and the effective target-host read grant need explicit review; a tenant predicate is not proof of per-private-card authorization.

Completeness is a hard precondition for absence/uniqueness claims. Row/page/byte/time/request/host budgets reject incomplete snapshots rather than truncate. GraphQL errors, missing fields, contradictory identity/counts/cursors/states and failed pages are UNKNOWN. GitHub's unsupported `Commit.pushedDate` cannot prove historic pushes: the persisted first-observed head timestamp is reset to arrival time on head changes (a conservative seven-day warmup for a changed SHA). New heads are seeded from head-bound evidence only (head check-suite `updated_at`, submitted review on the head commit, floored at `created_at`) rather than wall-clock arrival, so already-idle PRs trigger on discovery; PR-wide reviews or the card disposition line cannot date an unseen SHA. A head with no head-bound evidence stays UNKNOWN (no idle wake) until head-bound evidence arrives; later evidence seeds the retained head. Only a changed SHA gets an intentional arrival-time warmup. Seeded epochs never claim push time. A missing activity read suppresses idle but not a proven terminal-card trigger.

The state namespace is company/org/mode scoped. Live and dry-run receipts/cursors are separate. Stable trigger keys are shared across receipt, child `originId` and wake idempotency. Intent precedes create/wake; uncertain creation may be recovered only by exact origin, never repeated. Uncertain wake is never replayed. Failed intent persistence or a deadline guard before RPC invocation restores pending state; `queued:false` and the shared exact stock-host pre-enqueue refusal classifier can retry. Unknown transport/lost-reply errors remain unconfirmed. One worker per ledger, process-local overlap coalescing only; no cross-worker CAS/fencing claim. Hot receipt/clock maps cap at 20,000; bounded write-before-evict compaction archives settled receipts and stable clocks under exact company/org/mode-scoped hash keys. Every hot miss reads and validates its archive before allowing a new effect/clock; failed reads are UNKNOWN, not permission to replay. Pending/uncertain receipts remain hot and fail closed if unresolved work fills the cap. Archives never expire and require durable target-host storage capacity; backup/restore must retain both ledger and archives. Complete inventory retires only no-longer-open/monitored head observations; still-open clocks survive, while reappearing heads are re-observed as first observations and seeded from head-bound evidence (an already-idle reopened PR can trigger on discovery). Closed cursors retain inclusive second-precision overlap and never advance past undispatched/deferred/unconfirmed closure triggers or summaries containing that repository's closures. Open-only uncertainty stays UNKNOWN without pinning unrelated closure coverage. Inventory leaves 100 HTTP attempts and 30 seconds for dispatch. Durable per-repository PR-number continuations rotate expensive evidence reads without resetting head clocks; persisted effect-admission turns rotate deferred work and summaries under the shared cap, not by replaying uncertainty. Stable source/line fingerprints prevent unrelated metadata edits from refreshing a disposition. Actual child assignment/status/blockers are revalidated, not trusted from a cached child ID. Existing backstops and inspection of UNKNOWN/unconfirmed receipts are required for delivery gaps.

Caps are coded: 15 trigger effects/tick including uncertain creations, least-recently-effect-admitted first then oldest; 1,200 HTTP attempts, 20,000 host-read admissions, four-minute tick; 10,000 projected PR/head records; snapshot row/body/64-MiB aggregate bounds; inherited transport/cache/page/deadline/backoff controls. Audits retain at most 1,000 entries/30 days, use fixed outcomes and projected keys, and precede new effects. No provisioning, delegated credential, billable reservation or provider-resource TTL/auto-teardown applies because provider calls only read. Created native cards are accountable work, not automatically expired/deleted resources. The stock schema forces the namespace-migrate capability for read declarations; the active migration directory has no SQL and no runtime SQL write call exists. This capability remains part of the reviewed ceiling, not a claim that a compromised worker is read-only.

Operator compares the exact inventory to a manual REST inventory, verifies credential-visible coverage against the complete expected repository set, checks warmup/UNKNOWN explicitly, and proves native queue/dedup behavior before live use. Missing repository visibility cannot be discovered from a credential's own filtered listing; independent inventory comparison is mandatory. Disable custody and revoke its binding for rollback; do not erase receipt state. Security/QA source acceptance, target-host core-read/privacy/transport/idempotency evidence, Operator install/dry-run/live acceptance and later instruction/config-window adoption remain separate gates.

## Per-job addition: gates-status-sweep

This scheduled operation is separately disabled by default (`gatesStatusEnabled: false`), shadow-only by default (`gatesStatusShadow: true`), and registers no agent tool. `issue.updated` events enqueue and drain one card; the four-minute sweep drains the persisted queue for dropped events. It is the plugin's only GitHub write path.

| Credential/host ceiling | Gates exposes | Forbidden |
| --- | --- | --- |
| GitHub credential at write time | Fixed-origin POST `/repos/{owner}/{repo}/commits/{40hex}/statuses` with fixed context `paperclip/gates`, one of `success`/`failure`/`pending`, and a bounded generated description | Any other method/path, context, description, header, target URL, redirect follow, ETag-cached write, or status for an uncited SHA |
| App installation token | Same exchange endpoint, requesting exactly `statuses: write` (never combined with the read envelope), exactly one allowlisted repository, exact returned-scope/expiry validation | All-repo fallback, bearer/anonymous fallback, scope widening, agent-supplied App identity, installation/grant changes |
| Issue-thread interactions | `ctx.issues.listInteractions` for enqueued issues only; pure extraction: `request_confirmation` kind addressed to and resolved by the configured RM agent, terminal outcome, and the dedicated merge-authorization contract (title `Merge <owner/repo>#<n>?`, prompt identical to the title, details the bare PR URL, no summary/label/target/enrichment block), plus exactly one `owner/repo#N` and one distinct 40-hex SHA cited in the RM's resolution reason | Company/issue enumeration, treating generic or mis-addressed confirmations as merge authorization, trusting non-RM or ambiguous text, synthesizing statuses for new pushes, any issue update/comment tool |
| Plugin state | `gates-status-v1` instance ledger: queue (1,000), published map (2,000, 30-day retention), audits (1,000) | Storing credentials, JWTs, raw interaction bodies, or response bodies |

Fail-closed behavior is the point: without the App `statuses: write` grant the publisher logs `missing_permission` (403 from the POST or a short granted set at mint), records a per-SHA marker with a 60-second cooldown, retains the queue entry for retry with exponential backoff, and never publishes a green status. Missing-permission retries are a durable blocked state: they never count toward the general `maxAttempts` give-up, retry at capped 15-minute backoff, and publish once the grant arrives without needing another issue update. Intent is persisted before the POST; a restart after the POST is deduped by the published record, never replayed. Shadow mode computes and logs decisions with no credential resolution and no POST, and retains the authoritative shadow decision per SHA so the shadow→live flip publishes it on the next event/sweep. When a thread retains several RM decisions for one repo+SHA, only the authoritative one — greatest host decision time (`resolvedAt`, else `updatedAt`, else `createdAt`), interaction id as deterministic tie-break — is applied, and the published record persists that decision as a watermark: no older decision for the SHA can ever republish on any replay or host list order. Dedupe is otherwise per `repo+SHA+state`; a newer decision with a changed state (for example supersession to `pending`) publishes a new status. The per-SHA count is capped below GitHub's 1,000-statuses-per-SHA limit, after which further publishes stop and are audited as `cap_reached`. Per-tick budgets mirror the CI path: 240 HTTP requests, 180 seconds, 20 drain entries, and the shared single-worker lock. A disabled or invalid publisher performs no ledger writes at all on `issue.updated`. Residual risks: a delayed old status can only green the SHA the RM approved; retargeting an unprotected branch does not reach production; the ruleset requirement and App grant remain owner/Operator actions gated on shadow evidence, not effects of this plugin. Any live (`shadow: false`) publication requires the same independent Security acceptance, exact-head Actions evidence and production authorization as the other paths.

Security acceptance, QA, exact-head Actions/CodeQL/Devin, exact-artifact/host/configuration Security sign-off and applicable Release Manager production authorization remain independent gates before Operator installation enabled with dryRun=false.
